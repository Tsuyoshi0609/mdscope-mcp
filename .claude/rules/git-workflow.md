# git 運用ルール

`https://github.com/Tsuyoshi0609/mdscope-mcp.git`（`origin`）。**単独開発。ブランチを切らず
`main` に直接コミットし、`main` に push する。**

## push は毎回ユーザーの指示を待つ

| 操作 | 扱い |
|---|---|
| 編集・`add`・`commit` | **確認せず実行する。** 溜めてよい |
| `push origin main` | **その依頼があった、そのときだけ。** |
| ブランチ・PR | 使わない |

**「push して」は 1 回きりの許可であって、以後の許可ではない。** 前に言われたから、
コミットが溜まったから、区切りがよいから、は理由にならない。**push を打つ直前に
「いま、この push を頼まれたか」を確認する。** 頼まれていなければ打たない。

## 禁止

- **`push --force` / `--force-with-lease`、push 済みコミットの rebase・`filter-repo`**
- `reset --hard` / `clean -fdx` — **未追跡の実験データが消える**（再生成に GPU 時間）
- 秘密情報、大きなファイル・派生データのコミット

push 前のコミットの取り消しは `reset --soft HEAD~1`。

## `example/` の扱い

**`example/` 以下のデータは gitignore し、直下の `example/README.md` だけを追跡する。**
README には**取得手順だけ**を書く（出典 URL とファイル名）。データ本体・派生物（キャッシュ、
生成した HTML / PNG）は置かれていても追跡しない。

## 流れ

```bash
git pull origin main     # 別マシンの変更があるかもしれない
git status && git diff
git add <ファイル> && git commit -m "..."
git push origin main     # ← 指示を受けてから
```

`pull` がマージコミットを作ろうとしたり失敗したら、**そこで止まって確認する**。
`status` が汚れていたら先に片付ける（生成物は `.gitignore` へ）。

## いつコミットするか

「コミットしますか」と聞かずに、次のときその場で実行する。

1. **意味合いの異なる作業に移るとき** — 混ざったコミットを作らない
2. **同じ作業を 5 ラリー以上続けたとき** — 中途半端な編集は未コミットで置いてよい
3. **大規模な改修** — 終わりだけでなく**動く状態になるたび**
4. **セッション開始時のコミット残し** — 今の作業と無関係でも先に片付ける

## 分割とメッセージ

**1 コミット = 1 つの変更理由。** 基準は「これだけ読んで意味が通るか」「revert 単位か」。
ついでの整形、リファクタと機能追加は分ける。依存のある変更は動く順（実装 → テスト →
ドキュメント）。迷ったら細かい方へ。量が多くて判断がつかないときは**分割案を示してから**。

件名は英語の命令形、本文は日本語可で「なぜ」と「既知の制限」を書く。**未検証のものは
その旨を明記し、実測していない主張を断定形で書かない**。

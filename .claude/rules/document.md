# ドキュメントの書き方

**github公開を見据えて書く。** 読み手は「この手法を使いたい人」であって、開発の経緯を追いたい人ではない。
`docs/`・`docs/local/`・`.claude/rules/` は日本語。
コード内の docstring とコミット件名は既存の慣習に従う（件名は英語の命令形）。

**数式は GitHub でレンダリングされる形式**（`` $`...`$ `` と ```` ```math ```` ）。
`$...$` は壊れる。

## 1. どこに書くか — 振り分けの手順

新しく書く内容は、次の順に問うて置き場所を決める。同じことを 2 か所に書かない。

1. **セットアップ方法を理解するのに必要か？** → `docs/setup.md`
2. **使い方を理解するのに必要か？** → `docs/usage.md`
3. **現在の作業進捗を理解するのに要るか？** → `docs/progress.md`
   - 「現状と、これからの TODO の理解」に要るかどうか
   - 理由や判断の根拠は含めない
4. **ユーザーが困った時に参照するため、または、開発者が判断や失敗を繰り返さないために必要か？** → `docs/help.md`

## 2. 書かないこと

- **経緯・試行の順番・途中の迷い。** 話の流れは書かない
- **ファイルを見れば分かること**（実装の細部、関数の引数の網羅）。
- **試行段階の実装、採用しなかった案。** 1 行で済む理由以上のものは `docs/local/` へ
- **実測していない主張。** 「効いているはず」ではなく、保存物で確かめてから
- **定義していない言葉と、一目で意味が分からない言葉。** 内部の略号・変数名を、説明なしに文章・表・図に出さない。

**ただし重要な選択はミニマムに書く。** 省いてよいのは、読み飛ばしても手法の理解と再現が壊れないものだけ。次は書く —
手法の主張に直結する設定、間違えるとエラーを出さずに結果が変わる設定、設計判断そのもの。いずれも**値と一行の理由**まで。

## 3. 長さと数

- **1 ファイル 250 行以内。** 
- 超えたら、まずは不要な内容がないかまず検討する
- どうしても削れないなら、内容ごとに**分割**する。`docs/<doc-theme>.md` については `docs/<doc-theme>/<sub-theme>.md` に分割
- **1 フォルダ 10 文書まで。** 分割で数が増えるなら、先に統合できる文書が無いかを見る

## 4. 変更するとき

- **挙動を変えたら対応する `docs/` を同じコミットで直す**（既定値・フラグ名・出力パスは具体名で書かれている）
- **進捗の書き方は [progress.md](progress.md)**
- **古くなった記述はその場で消す。** 「旧方針」「以前は」の注記を積み重ねない。
